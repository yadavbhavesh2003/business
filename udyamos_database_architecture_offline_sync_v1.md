# UdyamOS --- Database Architecture + Offline Sync Engine

**Version 1.0 \| 19 November 2026 \| Engineering design draft**\
**Based on:** UdyamOS Technical PRD v1.0\
**Initial market:** India; Bhavnagar/Gujarat pilot\
**MVP:** Wholesale and textile traders (retail supported, not targeted); Android app (React Native + SQLite) +
web app (React + IndexedDB)

> This is an implementation blueprint, not a compliance certification. A
> qualified Indian GST practitioner/accountant must approve invoice
> numbering, tax calculation/rounding, statutory records and return
> workflows before production.

### Non-negotiable invariants

1.  "Saved on this device" appears only after the IndexedDB transaction
    commits.
2.  "Synced to cloud" appears only after server commit acknowledgement
    is persisted locally.
3.  Retrying an event never creates a second invoice, payment, stock
    movement or ledger effect.
4.  Posted records are not silently overwritten or hard-deleted.
5.  Tenant scope comes from authenticated membership, never from an
    untrusted client field.
6.  Stock balances are reconstructable from the stock movement ledger.
7.  Pull cursor advances only in the same local transaction that applies
    downloaded changes.
8.  Rejected/conflicted events remain visible and actionable.
9.  Offline data is not globally authoritative until server
    validation/acceptance.
10. A browser's background sync is opportunistic, not a guaranteed
    delivery mechanism.

## 2. Scope

**Included:** organisation, users/memberships, roles, branches, devices,
customers, suppliers, products, units, locations, sales invoices/lines,
purchases/lines, payments/allocations, stock movements/balances, audit,
idempotency, change log, local IndexedDB stores, outbox/inbox, conflict
queue, operational tests.

**Deferred:** full double-entry accounting, manufacturing BOM/work
orders/melt batches, multi-currency accounting, GST filing,
E-Invoice/E-Way Bill until authorised integration and compliance
validation, active-active multi-region, microservices, peer-to-peer
offline consensus.

Do not create speculative tables for every future vertical. Add domain
models when workflows are validated.

## 2A. Schema additions for the wholesale/textile wedge (v1.1)

The wedge segment (Technical PRD §0) needs these in the MVP schema:

-   **`stock_lots`**: `id, organisation_id, product_id, lot_code,
    roll_no, received_qty, uom, shade/design (nullable), purchase_line_id`.
    Textile stock is tracked by lot/roll, not only by product.
-   **`stock_movements` gains `lot_id` (nullable) and `godown_id`**.
    The balance projection is keyed by `(product, lot, godown)`.
-   **`delivery_challans` + `delivery_challan_lines`**: goods leave
    before invoicing. An invoice can reference one or more challans.
    Stock moves at challan time, never twice.
-   **`parties` gains `credit_limit`, `credit_days`, `block_on_overdue`**.
    The credit check runs locally (cached outstanding) and again on the
    server. An offline override is recorded as an audited exception.
-   **Device numbering series**: `numbering_series` is device-prefixed
    (e.g. `D03/25-26/000123`), pending CA approval (ADR-006).
-   **Negative stock**: allowed when offline, posted with a
    `negative_stock_flag` and listed in the owner's conflict review
    (ADR-008).

Do not add manufacturing, job-work costing or foundry tables yet.

### Online invoice transaction

1.  Authenticate and resolve active organisation membership.
2.  Check capability and branch scope.
3.  Validate request and idempotency key.
4.  Begin PostgreSQL transaction.
5.  Allocate invoice number using approved policy.
6.  Recalculate all totals server-side.
7.  Persist invoice header/lines and tax/calculation snapshots.
8.  Insert stock movements and update stock projection.
9.  Insert payment/receivable effects if in MVP scope.
10. Insert audit event and change-log rows.
11. Persist idempotency result.
12. Commit, then return stable IDs, number and server version.

Any failure rolls back all business effects.

### Offline invoice

1.  Generate stable invoice UUID and event UUID.
2.  Validate locally using a versioned deterministic rules package.
3.  In one IndexedDB transaction, save invoice, lines and immutable
    outbox event.
4.  Show **Saved on this device --- waiting to sync**.
5.  Push same event ID on reconnect.
6.  Server validates identity, permissions, references, tax policy,
    stock policy and numbering.
7.  Server returns `accepted`, `rejected` or `needs_resolution`.
8.  Persist acknowledgement locally.
9.  Preserve rejected records and show resolution steps; never silently
    discard.

## 4. Tenancy and access control

### 4.1 Identity model

-   `users`: global login identity.
-   `organisations`: business tenant.
-   `organisation_memberships`: user-to-tenant membership and role.
-   `roles`, `permissions`, `role_permissions`: capability model.
-   `branches`: business locations.
-   `user_branch_access`: optional branch restrictions.
-   `devices`: registered app installations, membership, platform, last
    seen and revocation.

A user may belong to multiple organisations. Do not infer tenant from
email domain or trust a client-supplied tenant ID.

### 4.2 Tenant columns and constraints

Every tenant-owned table must include: -
`organisation_id UUID NOT NULL` - `id UUID NOT NULL` -
`created_at TIMESTAMPTZ NOT NULL` - `updated_at TIMESTAMPTZ NOT NULL` -
optional `archived_at`

Use composite foreign keys `(organisation_id, referenced_id)` so a row
cannot point into another tenant.

### 4.3 Row-Level Security

Enable RLS on tenant-owned tables and set tenant context inside each
transaction using `SET LOCAL`, avoiding connection-pool leakage.

``` sql
ALTER TABLE customers ENABLE ROW LEVEL SECURITY;
ALTER TABLE customers FORCE ROW LEVEL SECURITY;

CREATE POLICY customers_tenant_policy ON customers
USING (organisation_id =
  current_setting('app.organisation_id', true)::uuid)
WITH CHECK (organisation_id =
  current_setting('app.organisation_id', true)::uuid);
```

The API runtime role must not own tables or have `BYPASSRLS`. Use a
separate migration role. Test RLS under the exact production runtime
role and pool configuration. RLS is defence in depth, not a substitute
for service-level permission checks.

## 6. PostgreSQL conventions

-   UUID primary keys; application-generated UUIDv7.
-   `TIMESTAMPTZ` for instants (UTC); `DATE` for business dates.
-   `NUMERIC`, never float/double, for money/tax/quantity.
-   `JSONB` only for versioned snapshots/metadata, not core relational
    fields.
-   `ON DELETE RESTRICT` for referenced financial/master data; archive
    instead.
-   `version BIGINT NOT NULL DEFAULT 1` on syncable mutable master
    records.
-   Store currency code and explicit rounding policy.
-   Suggested initial precision: amount `NUMERIC(19,4)`, unit price
    `NUMERIC(19,6)`, quantity `NUMERIC(20,6)`, tax rate `NUMERIC(9,6)`.
-   Decide line-level vs invoice-level tax rounding and discount
    allocation with an accountant/GST practitioner.
-   Snapshot product description, HSN, unit, price, discount, conversion
    factor and tax calculation on posted invoice lines.

Typical indexes: - `(organisation_id, normalized_name)` for
parties/products. -
`(organisation_id, branch_id, document_date DESC, id)` for document
lists. - `(organisation_id, product_id, location_id, occurred_at, id)`
for stock history. - `(organisation_id, sequence)` for sync pull. -
Partial indexes for active/non-archived records. - Add GIN/full-text
indexes only for measured query needs.

### 7.1 Organisation, user, membership, branch

``` sql
CREATE TABLE organisations (
  id UUID PRIMARY KEY,
  legal_name TEXT NOT NULL,
  display_name TEXT NOT NULL,
  country_code CHAR(2) NOT NULL DEFAULT 'IN',
  currency_code CHAR(3) NOT NULL DEFAULT 'INR',
  timezone TEXT NOT NULL DEFAULT 'Asia/Kolkata',
  default_language TEXT NOT NULL DEFAULT 'gu',
  business_type TEXT NOT NULL,
  gst_registration_status TEXT NOT NULL DEFAULT 'not_registered',
  gstin TEXT,
  financial_year_start_month SMALLINT NOT NULL DEFAULT 4
    CHECK (financial_year_start_month BETWEEN 1 AND 12),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE users (
  id UUID PRIMARY KEY,
  email TEXT UNIQUE,
  phone_e164 TEXT UNIQUE,
  password_hash TEXT,
  display_name TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active','invited','suspended','deleted')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE organisation_memberships (
  organisation_id UUID NOT NULL REFERENCES organisations(id),
  id UUID NOT NULL,
  user_id UUID NOT NULL REFERENCES users(id),
  role_code TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('invited','active','suspended','revoked')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (organisation_id, id),
  UNIQUE (organisation_id, user_id)
);

CREATE TABLE branches (
  organisation_id UUID NOT NULL REFERENCES organisations(id),
  id UUID NOT NULL,
  code TEXT NOT NULL,
  name TEXT NOT NULL,
  is_default BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  archived_at TIMESTAMPTZ,
  PRIMARY KEY (organisation_id, id),
  UNIQUE (organisation_id, code)
);

CREATE UNIQUE INDEX one_default_branch_per_org
ON branches (organisation_id)
WHERE is_default AND archived_at IS NULL;
```

### 7.6 Purchases

Create `purchases` and `purchase_lines` with the same
tenant/branch/document pattern: - supplier and supplier invoice
reference/date; - internal document number and status; - product,
quantity, unit and conversion factor; - cost, discount, taxable value,
tax components and line total snapshots; - source event ID unique per
organisation. Purchase posting and stock receipt must commit in one
database transaction. Decide whether duplicate supplier invoice
references warn or block; do not assume all suppliers follow identical
numbering practices.

### 7.7 Stock movement ledger and projection

``` sql
CREATE TABLE stock_movements (
  organisation_id UUID NOT NULL,
  id UUID NOT NULL,
  branch_id UUID NOT NULL,
  location_id UUID NOT NULL,
  product_id UUID NOT NULL,
  movement_type TEXT NOT NULL CHECK (movement_type IN (
    'opening','purchase_receipt','sale_issue','sales_return',
    'purchase_return','adjustment_in','adjustment_out',
    'transfer_in','transfer_out','reversal'
  )),
  quantity_delta NUMERIC(20,6) NOT NULL CHECK (quantity_delta <> 0),
  base_unit_code_snapshot TEXT NOT NULL,
  source_type TEXT NOT NULL,
  source_id UUID NOT NULL,
  source_line_id UUID,
  occurred_at TIMESTAMPTZ NOT NULL,
  recorded_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  actor_user_id UUID NOT NULL,
  device_id UUID,
  reversal_of_movement_id UUID,
  event_id UUID,
  PRIMARY KEY (organisation_id, id),
  FOREIGN KEY (organisation_id, branch_id)
    REFERENCES branches(organisation_id, id),
  FOREIGN KEY (organisation_id, location_id)
    REFERENCES locations(organisation_id, id),
  FOREIGN KEY (organisation_id, product_id)
    REFERENCES products(organisation_id, id)
);

CREATE INDEX stock_movement_history
ON stock_movements
(organisation_id, product_id, location_id, occurred_at, id);

CREATE TABLE stock_balances (
  organisation_id UUID NOT NULL,
  product_id UUID NOT NULL,
  location_id UUID NOT NULL,
  on_hand NUMERIC(20,6) NOT NULL DEFAULT 0,
  last_movement_at TIMESTAMPTZ,
  projection_version BIGINT NOT NULL DEFAULT 1,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (organisation_id, product_id, location_id),
  FOREIGN KEY (organisation_id, product_id)
    REFERENCES products(organisation_id, id),
  FOREIGN KEY (organisation_id, location_id)
    REFERENCES locations(organisation_id, id)
);
```

Rules: 1. `quantity_delta` is in base units; receipts positive, issues
negative. 2. Movements are append-only; corrections use reversal +
replacement. 3. Insert movement and update projection in the same
transaction. 4. Lock balance row (`SELECT ... FOR UPDATE`) or use tested
atomic upsert. 5. Transfer creates paired negative/positive movements
atomically. 6. Negative-stock policy is explicit and enforced under
lock. 7. Offline stock is only a device-local estimate. Server
revalidates when event arrives. 8. Reconcile `stock_balances` against
`SUM(stock_movements.quantity_delta)` regularly.

### 7.8 Payments and allocations

``` sql
CREATE TABLE payments (
  organisation_id UUID NOT NULL,
  id UUID NOT NULL,
  branch_id UUID NOT NULL,
  party_type TEXT NOT NULL CHECK (party_type IN ('customer','supplier')),
  party_id UUID NOT NULL,
  direction TEXT NOT NULL CHECK (direction IN ('received','paid')),
  payment_method TEXT NOT NULL,
  amount NUMERIC(19,4) NOT NULL CHECK (amount > 0),
  currency_code CHAR(3) NOT NULL DEFAULT 'INR',
  payment_date DATE NOT NULL,
  reference_number TEXT,
  status TEXT NOT NULL CHECK (status IN
    ('pending_sync','posted','reversed','rejected')),
  source_event_id UUID,
  created_by UUID NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (organisation_id, id),
  UNIQUE (organisation_id, source_event_id)
);

CREATE TABLE payment_allocations (
  organisation_id UUID NOT NULL,
  id UUID NOT NULL,
  payment_id UUID NOT NULL,
  document_type TEXT NOT NULL CHECK
    (document_type IN ('sales_invoice','purchase')),
  document_id UUID NOT NULL,
  allocated_amount NUMERIC(19,4) NOT NULL CHECK (allocated_amount > 0),
  PRIMARY KEY (organisation_id, id),
  FOREIGN KEY (organisation_id, payment_id)
    REFERENCES payments(organisation_id, id)
);
```

`document_id` is polymorphic here and therefore cannot have a normal FK
to multiple tables. For stronger integrity, use separate typed
allocation tables or enforce document existence and same-tenant
ownership transactionally in domain code. Enforce allocation sums
against payment amount and document outstanding.

## 8. Audit, idempotency and change log

### 8.1 Audit

Store organisation, actor, branch, device, action, entity type/ID,
reason, correlation ID, occurred/recorded timestamps and redacted
metadata. Audit is append-only. Never log passwords, tokens, payment
credentials or unnecessary invoice payloads.

### 8.2 Idempotency

``` sql
CREATE TABLE idempotency_records (
  organisation_id UUID NOT NULL,
  id UUID NOT NULL,
  idempotency_key TEXT NOT NULL,
  request_hash TEXT NOT NULL,
  response_status INTEGER,
  response_body JSONB,
  resource_type TEXT,
  resource_id UUID,
  state TEXT NOT NULL CHECK (state IN ('processing','completed','failed')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (organisation_id, id),
  UNIQUE (organisation_id, idempotency_key)
);
```

Algorithm: 1. Require a key for retriable financial mutations. 2.
Canonicalise request and hash it. 3. Insert under unique constraint. 4.
Existing key + different hash → `409 IDEMPOTENCY_KEY_REUSED`. 5.
Existing completed key → return stored result. 6. Store idempotency
result and business mutation in the same transaction. 7. Expire bulky
response bodies by policy, but retain durable event IDs on business
records.

### 8.3 Tenant change log

``` sql
CREATE TABLE tenant_change_counters (
  organisation_id UUID PRIMARY KEY REFERENCES organisations(id),
  last_sequence BIGINT NOT NULL DEFAULT 0
);

CREATE TABLE change_log (
  organisation_id UUID NOT NULL,
  sequence BIGINT NOT NULL,
  id UUID NOT NULL,
  entity_type TEXT NOT NULL,
  entity_id UUID NOT NULL,
  operation TEXT NOT NULL CHECK (operation IN ('upsert','tombstone')),
  entity_version BIGINT NOT NULL,
  branch_id UUID,
  changed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (organisation_id, sequence),
  UNIQUE (organisation_id, id)
);
```

Allocate `last_sequence` under row lock inside the same transaction as
domain mutation and change-log insertion. Do not assume a plain
sequence/BIGSERIAL guarantees commit ordering without gaps. Cursor is
opaque, tenant-scoped and protocol-versioned. For high-volume tenants,
measure whether the per-tenant counter becomes a bottleneck before
redesigning.

## 9. IndexedDB local data model

Use one persistence abstraction; React components must never access
IndexedDB directly.

Suggested stores: - `meta`: schema version, device ID, active
organisation, last pull cursor, last sync time. - `customers`,
`suppliers`, `products`, `units`, `locations`: cached entities with
`serverVersion`, `localVersion`, `syncState`. - `salesInvoices`,
`salesInvoiceLines`, `purchases`, `purchaseLines`, `payments`. -
`stockMovements`, `stockBalances`: cached server data + local pending
movements. - `outbox`: immutable events awaiting acknowledgement. -
`inbox`: pull batch/deduplication metadata. - `conflicts`:
rejected/conflicting records and resolution state. - `tombstones`:
archived/deleted IDs and versions. - `attachments`: upload metadata;
large files use managed upload queue. - `syncRuns`: redacted diagnostic
history.

Suggested indexes: - Entities: `[organisationId+normalizedName]`,
`[organisationId+updatedAt]`, `[organisationId+syncState]`. - Outbox:
`eventId` primary key, `[status+nextAttemptAt]`,
`[aggregateType+aggregateId]`, `createdAt`. - Conflicts:
`[status+createdAt]`.

One active organisation context per device is simplest. On organisation
switch, all repository operations must scope by organisation. Never mix
cached rows across tenants.

### Atomic local invoice save

One IndexedDB read-write transaction must: 1. Save invoice header. 2.
Save invoice lines. 3. Save local stock preview rows if needed. 4. Save
immutable outbox event and payload hash. 5. Set local document status to
`pending_sync`. 6. Commit.

On quota/storage failure, show **Could not save on this device**.
Request persistent storage where supported, but never promise browser
data cannot be evicted.

## 10. Outbox event contract

### 10.1 Event envelope

``` json
{
  "protocolVersion": 1,
  "eventId": "uuid",
  "eventType": "sales.invoice.create",
  "eventSchemaVersion": 1,
  "organisationId": "tenant-uuid",
  "branchId": "branch-uuid",
  "deviceId": "device-uuid",
  "actorMembershipId": "membership-uuid",
  "deviceSequence": 42,
  "aggregateType": "sales_invoice",
  "aggregateId": "invoice-uuid",
  "aggregateLocalVersion": 1,
  "occurredAt": "2026-11-19T12:00:00.000Z",
  "baseServerVersion": null,
  "idempotencyKey": "device-uuid:42",
  "payloadHash": "sha256-canonical-payload",
  "payload": {"customerId":"uuid","documentDate":"2026-11-19","lines":[]}
}
```

`organisationId` is informational; server derives tenant from
authenticated membership and rejects mismatch. Decimal values in
payloads are strings, not JS floating-point numbers. Canonical JSON
hashing must specify key ordering, number formatting, Unicode
normalisation and null handling.

### 10.2 Immutability and states

Once enqueued, event ID/type/schema/aggregate/payload are immutable.
Correct an in-flight event with an explicit superseding event, not
silent payload mutation.

States: - `pending` → `in_flight` → `accepted` - `in_flight` →
`retry_wait` for transient failures - `in_flight` → `rejected` for
permanent validation failures - `in_flight` → `needs_resolution` for
business conflicts - `retry_wait` → `pending` when due

`accepted` is terminal for that event. Later correction is a new
reversal/amendment event.

### 10.3 Push API

`POST /api/v1/sync/push`

Request includes `protocolVersion` and bounded `events[]`. Each event
contains event ID/type/schema version, device sequence, idempotency key,
payload hash and payload.

Per-event response:

``` json
{
  "results": [{
    "eventId": "uuid",
    "status": "accepted",
    "resourceType": "sales_invoice",
    "resourceId": "uuid",
    "serverVersion": 1,
    "documentNumber": "assigned-by-approved-policy",
    "serverChangeCursor": "opaque-token"
  }]
}
```

Allowed statuses: `accepted`, `duplicate_accepted`, `retryable_error`,
`rejected`, `needs_resolution`. Include stable machine code and safe
user message. Never expose SQL errors.

### 10.4 Server event processing

1.  Authenticate; resolve active membership and registered device.
2.  Reject revoked device or mismatched tenant.
3.  Validate protocol/event schema version.
4.  Recompute payload hash.
5.  Insert event under unique `(organisation_id,event_id)`.
6.  Duplicate event returns prior result without reapplying.
7.  Validate same-tenant master references and branch permissions.
8.  Recalculate values and run domain validation.
9.  Apply mutation, audit and change-log rows in one transaction.
10. Store event result and commit.
11. Return per-event acknowledgement.

Bound batch size (start with 20--100 events, then load-test). Process
each event independently so one invalid event does not block unrelated
events, unless a documented aggregate needs atomic grouping.

## 11. Pull protocol and cursor safety

`GET /api/v1/sync/pull?cursor=<opaque>&limit=500`

Example:

``` json
{
  "protocolVersion": 1,
  "nextCursor": "opaque-token",
  "hasMore": true,
  "changes": [{
    "sequence": 105,
    "entityType": "product",
    "entityId": "uuid",
    "operation": "upsert",
    "entityVersion": 8,
    "branchId": "uuid",
    "data": {}
  }]
}
```

Rules: - Cursor is opaque, tamper-resistant, organisation-scoped and
protocol-versioned. - Return changes strictly after cursor, ordered by
tenant sequence. - Client applies page and persists `nextCursor` in one
IndexedDB transaction. - If apply fails, cursor remains unchanged;
re-fetch is safe. - Repeated page delivery is idempotent. - Include
tombstones for archived/deleted entities. - If retention compacts
history, expired cursor returns `CURSOR_EXPIRED` and triggers full
authorised resnapshot.

### Full resnapshot

1.  Obtain snapshot token and watermark.
2.  Download tenant/branch-scoped pages into staging stores.
3.  Verify page completeness/checksums.
4.  Atomically activate snapshot and cursor watermark.
5.  Replay changes after watermark.
6.  Preserve unsynced outbox events.
7.  Never overwrite local pending edits without conflict handling.

## 12. Conflict policy

  -----------------------------------------------------------------------
  Entity/action                       Policy
  ----------------------------------- -----------------------------------
  Master create                       Stable client UUID; server dedupe;
                                      natural-key duplicates may prompt
                                      merge

  Master edit                         Optimistic concurrency with
                                      `baseServerVersion`; stale version
                                      returns conflict/diff

  Archive                             Tombstone and version; preserve
                                      historical references

  Invoice draft                       Editable locally until event
                                      emitted; then immutable event or
                                      superseding event

  Posted invoice                      Append-only; return/credit
                                      note/cancellation workflow

  Invoice number                      Server-approved strategy; no
                                      independent shared offline counters

  Payment                             Idempotent append-only; reversal
                                      for correction

  Stock movement                      Append-only; server revalidates
                                      stock

  Last unit sold offline on two       Apply explicit negative-stock
  devices                             policy or mark later event
                                      `needs_resolution`

  User/role revocation                Reject new sync after revocation;
                                      offline device learns only after
                                      reconnect

  Price change                        Snapshot price locally; server
                                      policy decides honour vs approval

  Tax rule change                     Snapshot tax version/effective
                                      date; validate server-side
  -----------------------------------------------------------------------

For mutable masters, send `baseServerVersion`. Server updates only if
current version matches; otherwise return `409 VERSION_CONFLICT` with
current version and safe field diff. Do not merge dependent fields
blindly.

Offline stock is only a local estimate based on last pull plus that
device's pending movements. Label it with last sync time. The server
cannot know what another disconnected device sold. Never silently change
invoice quantity/price/date during reconciliation.

## 13. Invoice numbering --- production blocker

Do not implement a shared naive offline integer counter.

Options to evaluate with GST practitioner: 1. **Reserved number
ranges:** server reserves non-overlapping blocks per
device/branch/series; define unused-number and lost-device policy. 2.
**Device/branch series:** reduce collisions but validate statutory and
customer requirements. 3. **Provisional local reference:** offline
record is not represented as a final tax invoice; server assigns final
number after acceptance.

Before final invoice PDF/printing, sign off: - legal meaning/timing of
invoice issuance; - sequential series and gaps; - multi-device
same-branch behaviour; - offline rejection handling; - printed/shared
provisional document wording; - return/credit-note references.

Until approved, offline workflow may save a provisional sales
record/draft only. Do not claim it is a compliant final tax invoice.

## 14. Retry, scheduling and crash recovery

### Trigger strategy

Sync on app launch, network recovery, after local transaction commit,
explicit "Sync now", and periodically while app is active. Do not rely
on Background Sync alone; browsers may suspend work.

### Retry

Exponential backoff with jitter (example: 2--5 sec, 5--15 sec, 15--45
sec, then 1--5 min capped). Retry timeouts, 429 and transient 5xx.
Honour `Retry-After`. Do not auto-retry permanent validation errors.
Pause on auth expiry and ask user to sign in.

### Crash cases

-   Before local commit: no success shown.
-   After local commit: outbox survives app restart.
-   Request reaches server, response lost: retry same event ID; server
    returns prior result.
-   Server commits, client fails to persist ack: retry safely.
-   Pull changes applied, crash before cursor commit: re-fetch and
    reapply idempotently.
-   Storage evicted/corrupted: restore server-synced snapshot where
    possible; unsynced local-only records may be unrecoverable. State
    this honestly.

### User-facing states

-   **Saved on this device**
-   **Waiting for internet**
-   **Syncing**
-   **Synced to cloud**
-   **Needs your attention**
-   **Could not save on this device**

Always show last successful sync and pending count. Never use ambiguous
"Saved" when only local storage succeeded.

## 15. Security controls

-   TLS for all API traffic.
-   Short-lived access credentials and refresh-token rotation; use
    secure cookie design for web sessions where appropriate.
-   Device bound to membership; support revocation.
-   Strict versioned payload validation, size/batch limits and rate
    limits.
-   Payload hash detects mismatch but is not proof of a trusted client.
-   Never trust actor, tenant, role, branch access or totals from
    payload without server-side resolution.
-   Event ID/idempotency uniqueness prevents replayed effects.
-   Parameterised SQL; secrets never in local storage or logs.
-   Encrypt backups and object storage; define key rotation.
-   Restrict/log support access and impersonation.
-   Define retention/deletion policy with legal holds.
-   Test IDOR/cross-tenant access on API and file downloads.
-   Device signing keys may be considered for native clients; browser
    key protection has limitations.

## 16. Migration and deployment

-   Production migrations are forward-only; rollback is a corrective
    migration.
-   Every migration has ID, author, timestamp, description and checksum.
-   Migration role is separate from API runtime role.
-   Use expand-and-contract for large schema changes.
-   Avoid long locks; use concurrent index creation where appropriate.
-   Test migrations against realistic data and restored backup.
-   Never edit an applied migration; add a new one.
-   Separate local/test/staging/production databases, buckets,
    credentials and secrets.
-   Use synthetic/anonymised staging data; do not copy production data
    to laptops by default.
-   Seed stable reference data only: roles/permissions, common units,
    reviewed tax metadata, language metadata, default branch/location.
    Demo data belongs in a demo tenant.

## 17. Reconciliation and monitoring

Monitor: - pending/failed outbox count by tenant/device; - oldest
pending event age; - rejection/conflict/duplicate rate by event type; -
pull cursor lag and expired cursor count; - invoice header totals vs
line totals; - payment allocation totals vs payment amount; - stock
projection vs movement-ledger sum; - documents missing expected stock
movements; - duplicate invoice numbers; - audit/change-log insertion
failures; - database storage, connections, slow queries and backup
status.

Alert on any invoice-number collision, stock projection mismatch,
cross-tenant test failure, backup failure, old pending financial event
beyond agreed threshold, sustained rejection spike or connection
saturation.

Reconciliation jobs: - Stock: sum movements by tenant/product/location
and compare projection. - Invoice: compare header totals with line/tax
snapshots. - Payments: compare allocations and outstanding. - Change
log: verify sync-visible changes have change records. - Audit: verify
sensitive actions have audit entries.

A mismatch creates an investigation record; do not auto-edit financial
history.

## 21. Initial ADRs

-   **ADR-001 Modular monolith:** one deployable backend, clear domain
    modules; revisit only when scale/team boundaries justify services.
-   **ADR-002 Shared PostgreSQL + tenant key + RLS:** economical SaaS
    model with layered isolation; requires strict RLS/pool tests.
-   **ADR-003 Append-only financial and stock posting:** reversal
    workflows preserve traceability.
-   **ADR-004 Transactional outbox:** local document/outbox and server
    event/domain mutation are atomic.
-   **ADR-005 Opaque pull cursor:** client persists cursor only after
    applying changes.
-   **ADR-006 No generic last-write-wins:** conflicts are
    domain-specific.

## 22. Final recommendation

Build one end-to-end vertical slice before expanding every module:

**Create organisation → add product/customer → create invoice offline →
atomically save invoice and outbox → reconnect → push event → server
validates/posts → acknowledgement returns → device marks cloud-synced →
pull remote product update → verify tenant isolation and stock
reconciliation.**

Test app crashes, network loss, duplicate requests, two-device
concurrency and tenant isolation. If this workflow is not reliable, do
not expand the feature set.

**The hardest part is not creating tables. It is preserving business
truth when multiple devices work offline and reconnect later.**
